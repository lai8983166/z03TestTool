## Context

`flow.js` 通过隐藏窗口 helper 驱动上位机服务页面。搜索能力流程共用 `runSearchFlow`，录制结束后由 `stopAcquisitionAndSave` 停止切换式保存和A帧发送；数据保存为上位机服务数据目录中的 `数据采集AB帧_*.xlsx`，B帧工作表第一行为字段名。

## Goals / Non-Goals

**Goals:**

- 用与搜索能力相同的15秒采集基础设施实现独立「帧频」流程。
- 按B帧表头定位「红外图像帧号」，在不依赖固定列号的前提下统计最长的相邻差为2连续记录。
- 让搜索流程的收尾A帧在停止采集前发送，并复用现有异步停止竞态处理。

**Non-Goals:**

- 不修改上位机服务的帧号生成、保存格式或页面代码。
- 不把帧频结果扩展为帧率单位换算；本流程只验证连续帧号间隔和数量。
- 不改变搜索能力各波位的点判定规则、平均时间除以5和范围计算方式。

## Decisions

1. **复用现有录制生命周期**：新增流程使用“停止遗留状态→启动A帧→启动保存→15秒→收尾清理”的相同切换按钮逻辑，避免不同流程对后台发送状态的处理不一致。备选方案是复制一套采集代码，维护成本和竞态风险更高。
2. **按表头文字定位帧号列**：读取B帧第一行，选择包含「红外图像帧号」的列并解析每行数值；这样兼容列顺序变化。缺列、空表和无效值全部作为失败，不用固定列号兜底。
3. **连续性定义**：对有效帧号按文件顺序扫描，当前值减前一值等于2则连续计数加一，否则从当前值重新开始；连续计数按记录数计算，达到1000条记录即成功。这样“连续1000帧前后差距为2”具有可测试且明确的边界。
4. **搜索收尾顺序**：在正常录制结束的 `try` 主路径中先切换截获/预置状态并点击更新A帧，再进入 `finally` 停止保存和发送。异常路径不强制发送预置A帧，只保证已有任务停止，避免在页面状态不完整时继续操作。
5. **帧频流程的结果输出**：日志输出总有效帧数、最长连续数量、目标数量和成功/失败原因；不对成功帧段再做时间平均。

## Risks / Trade-offs

- [B帧存在无效帧号或重复帧] → 无效值打断当前连续段，并从下一个有效数值重新计数；日志保留有效帧总数和最长连续数。
- [更新A帧会异步重启发送循环] → 继续使用现有重复核验停止逻辑，确认收尾A帧发送后再稳定停止。
- [“1000帧”按记录数而非间隔数解释] → 规格明确为连续1000条帧号记录；若设备验收口径要求1000个间隔，可只调整阈值定义和测试。

## Migration Plan

无需迁移；更新应用代码和侧边栏即可。使用新的便携版EXE时仍从旁边的 `config.json` 读取上位机路径。
